# 00. 도메인 설계

우리는 **PG(결제대행사)** 다. 가맹점 대신 카드사에 결제 승인을 받고, 다음 날 카드사가 보내는 매입 내역과 우리 승인 기록을 대사한 뒤, 수수료를 떼고 가맹점에 정산금을 지급한다.

## 1. 범위

| 포함 (v1) | 제외 (완성선 이후) |
|---|---|
| 승인, 전체 취소 API | 부분 취소 |
| 가상 카드사와 고정길이 전문 통신, 망취소 | 매입 청구 파일 송신 (v1은 카드사가 매입 내역을 보내준다고 가정) |
| 매입 내역 파일 수신·검증 | 카드사 → PG 입금 대사, PG 수익 정산 |
| 대사 (승인 vs 매입) | 대사 불일치 처리 화면 (React) |
| 가맹점 정산 (수수료, 부가세, 지급일) | 음수 정산의 상계·이월 |
| 지급 파일 생성 | 실제 은행 송신, K3s 배포 |

## 2. 용어

| 용어 | 뜻 |
|---|---|
| 승인 (Authorization) | 카드사가 결제를 허락하는 것. 카드사가 승인번호를 발급한다. 돈은 아직 움직이지 않는다. |
| 취소 | 승인된 거래를 되돌리는 요청. 취소도 자기 거래고유번호를 가진다. |
| 망취소 (Network Cancel) | 요청을 보냈는데 응답을 못 받았을 때(타임아웃), **카드사 쪽 결과를 모르니** 그 거래를 무효로 만드는 전문. 카드사가 승인했었다면 취소되고, 아니었다면 아무 일도 없다. |
| 매입 (Acquisition) | 카드사가 승인 거래를 청구 대상으로 확정하는 것. 이때부터 돈이 움직인다. |
| 매입 취소 | 매입 이후에 취소된 거래. 매입 내역 파일에 음수 성격의 레코드로 온다. |
| 대사 (Reconciliation) | 두 기록(우리 승인 원장, 카드사 매입 내역)을 맞춰 보고 불일치를 찾는 것. |
| 정산 (Settlement) | 가맹점별로 받을 돈을 계산하는 것. 거래 금액 − 취소 − 수수료 − 부가세. |
| 지급 (Payout) | 정산금을 가맹점 계좌로 보내는 것. v1은 은행에 보낼 지급 파일 생성까지. |
| 전문 (Message) | 기관 간에 주고받는 고정길이 바이트 메시지. 명세는 [02-message-spec.md](02-message-spec.md). |
| 거래고유번호 (`txn_id`) | 우리가 거래마다 만드는 20바이트 ID. 망취소와 대사에서 원거래를 찾는 키. |
| 매입일 (`business_date`) | 매입 내역 파일의 기준일. 정산 배치의 파라미터. |
| 지급일 (`payout_date`) | 매입일 + 가맹점 정산주기(영업일). 주말과 휴일 테이블의 날짜는 건너뛴다. |
| 선분이력 | 기간별로 바뀌는 값을 `시작일 ~ 종료일` 행으로 관리하는 테이블 패턴. 수수료율에 쓴다. |

## 3. 시간 순서로 본 흐름

```
D일 낮       가맹점 → [승인 API] → 전문 0100 → 카드사 → 0110 응답 → 승인 원장 저장
D+1 새벽     카드사 → 매입 내역 파일 (D일 승인분)
D+1 배치 ①   매입 파일 검증·적재 (헤더·트레일러 건수와 합계 확인)
D+1 배치 ②   대사: 승인 원장 vs 매입 내역 → 불일치 기록
D+1 배치 ③   정산: 가맹점별 금액, 수수료, 부가세, 지급일 계산
지급일 새벽   지급 파일 생성 (그날 지급할 정산 전부)
```

**지급일 예시** — 매입일 2026-10-08(목), 정산주기 D+2 영업일:
10-09(금, 한글날) 휴일 → 10-10(토)·10-11(일) 주말 → 10-12(월) 1영업일 → 10-13(화) 2영업일 → **지급일 10-13**.
대체공휴일처럼 요일만으로 계산할 수 없는 휴일이 있으므로 휴일은 테이블로 관리한다.

## 4. 승인 거래의 상태 전이

**결제 (`payment`)**
```
REQUESTED ──0110 정상──▶ APPROVED ──취소 성공──▶ CANCELLED
    │
    ├──0110 거절, 연결 실패──▶ DECLINED
    │
    └──응답 확인 실패──▶ UNKNOWN ──망취소 0430 수신──▶ NET_CANCELLED
```

- **전송 전에 REQUESTED로 먼저 저장**한다. 그래야 전송 후 앱이 죽어도 "보냈을지도 모르는 거래"가 기록에 남는다.
- **연결 실패는 망취소 없이 DECLINED다.** 연결이 안 됐으면 전문이 나가지 않은 게 확실하다. 연결된 뒤의 실패(타임아웃, 응답 전문 오류)는 카드사가 받았을 수 있으므로 UNKNOWN이다.
- **UNKNOWN은 절대 APPROVED로 취급하지 않는다.** 결과를 모르면 망취소로 정리하고 가맹점에는 실패로 응답한다.
- 망취소 재시도가 모두 실패하면 UNKNOWN으로 남는다. 다음 날 대사에서 매입이 들어오면 불일치로 잡힌다.

**취소 (`payment_cancel`)** — 결제 하나에 취소 시도가 여러 번 있을 수 있다.
```
REQUESTED ──0410 정상, 2002 이미 취소됨──▶ CANCELLED       결제도 CANCELLED
    │
    ├──0410 거절, 연결 실패──▶ FAILED                      결제는 APPROVED 그대로
    │
    └──응답 확인 실패──▶ UNKNOWN ──망취소──▶ NET_CANCELLED   결제는 APPROVED 그대로
```

- FAILED나 NET_CANCELLED로 끝나면 같은 결제를 다시 취소할 수 있다. 결과를 모르는 취소(UNKNOWN)가 있으면 새 취소를 막는다. 이유는 [03-api.md](03-api.md) 5장.

## 5. 대사 결과 유형

| 유형 | 뜻 | 대표 원인 |
|---|---|---|
| `MATCHED` | 승인과 매입이 일치 | 정상 |
| `UNCAPTURED` | 매입(또는 매입취소)이 와야 하는데 없음 | 카드사 누락 |
| `AMOUNT_MISMATCH` | 둘 다 있는데 금액이 다름 | 어느 한쪽 오류 |
| `STATUS_MISMATCH` | 우리가 실패·취소로 정리한 거래에 매입이 들어옴 | 취소 전문 유실, 망취소 미확정(UNKNOWN), 서버 중단으로 남은 REQUESTED |
| `CAPTURE_ONLY` | 매입은 있는데 우리 기록이 없음 | 다른 경로 거래 혼입, 데이터 유실 |

v1의 시뮬레이터는 승인 다음 날 바로 매입하므로, 매입일 D+1 파일은 D일 승인분과 비교한다. 실제로는 매입이 며칠 늦게 올 수 있어 `UNCAPTURED`를 바로 확정하지 않고 대기 기간을 두지만, v1은 생략한다.

- **비교 기준은 지금 상태가 아니라 D일 24:00 시점의 상태다.** D일에 승인되고 D+1 새벽에 취소된 거래는, 지금은 CANCELLED지만 D+1 파일에는 매입으로 와야 맞다.
- 매입취소(`02`)도 같은 다섯 유형으로 대사한다. 매입 후에 취소된 거래는 취소 다음 날 파일에 매입취소로 온다. 매입취소가 누락되면 가맹점에 돈을 더 주게 된다.
- 대사 SQL과 기준 시점 계산은 [04-batch.md](04-batch.md).

## 6. 불변식

| # | 규칙 | 강제 위치 |
|---|---|---|
| I1 | 거래고유번호는 유일하다 | DB `UNIQUE` |
| I2 | 가맹점의 같은 `Idempotency-Key` 요청은 한 번만 처리된다 | DB `UNIQUE (merchant_id, idempotency_key)` |
| I3 | 상태 전이는 4장의 화살표만 허용한다 | 도메인 코드 + `UPDATE … WHERE status = :기대상태` |
| I4 | 매입 파일의 트레일러 건수·합계 = 실제 데이터 레코드의 건수·합계. 다르면 **파일 전체를 거부**한다 | 배치 ① 검증 + 적재 트랜잭션 롤백 |
| I5 | 매입 레코드 하나는 대사 결과 하나에만 쓰인다 | DB `UNIQUE (acquisition_record_id)` |
| I6 | 정산 금액: 지급액 = 거래 합계 − 취소 합계 − 수수료 − 부가세 | DB `CHECK` |
| I7 | 지급 파일 트레일러 합계 = 포함된 정산 지급액 합계 | 배치 검증 |
| I8 | 금액은 원 단위 정수다. 계산에 `double`을 쓰지 않는다 | 코드 규칙 + DB `NUMBER(15)` |
| I9 | 수수료율 선분이력은 가맹점별로 기간이 겹치지 않는다 | 코드 + 검증 쿼리 (Oracle에는 Postgres의 배제 제약이 없음) |
| I10 | 카드번호를 평문으로 저장·로그하지 않는다 | 암호화 컬럼 + 전문 로그 마스킹 ([ADR-0005](adr/0005-card-data-protection.md)) |

## 7. 규모 계산

**가정:** 중형 PG, 가맹점 1,000곳, 하루 승인 100만 건.

- **온라인:** 100만 ÷ 86,400초 ≈ 평균 **11.6 TPS**, 점심·저녁 집중을 10배로 잡아도 **약 116 TPS**. 온라인은 무겁지 않다. 이 프로젝트의 무게 중심은 **배치**다.
- **매입 파일:** 100만 레코드 × 150바이트 = **150MB**.
- **배치 윈도:** 새벽 배치를 2시간 안에 끝내야 한다면 100만 ÷ 7,200초 ≈ **초당 139건 이상** 처리해야 한다.
- **chunk 크기:** 건당 처리 0.5ms, 커밋 1회 20ms라고 하면 chunk 1,000은 약 520초, chunk 10은 약 2,500초. 실제 값은 Phase 4에서 측정한다.
