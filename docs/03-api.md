# 03. 승인 API 계약

계약 원본: [`api/openapi.yaml`](api/openapi.yaml). 이 문서는 **왜 그렇게 정했는지**를 적는다.

## 엔드포인트

| 메서드 · 경로 | 용도 | 보내는 전문 |
|---|---|---|
| `POST /v1/payments` | 승인 | 0100, 실패 시 0420 |
| `GET /v1/payments/{txnId}` | 조회 | — |
| `POST /v1/payments/{txnId}/cancel` | 전체 취소 | 0400, 실패 시 0420 |

인증은 가맹점별 `X-Api-Key`다. 승인 요청에는 `Idempotency-Key`가 필수다.

## 1. 카드사까지 간 요청은 결과를 본문으로 돌려준다

| 상황 | HTTP | `status` | `result.code` |
|---|---|---|---|
| 승인 | 201 | `APPROVED` | `0000` |
| 카드사 거절 | 201 | `DECLINED` | `1001` 등 |
| 카드사 연결 실패 | 201 | `DECLINED` | `P001` |
| 응답 확인 실패 → 망취소 완료 | 201 | `NET_CANCELLED` | `P002` |
| 응답 확인 실패 → 망취소도 실패 | 201 | `UNKNOWN` | `P003` |
| 형식 오류, 인증 실패, 멱등 키 충돌 | 4xx | — | — |

기준은 **결제 행(`REQUESTED`)을 만들었느냐**다. 만들었으면 결과가 무엇이든 그 행을 돌려주고, 만들기 전에 막혔으면 4xx다. 그래서 가맹점이 지킬 규칙은 하나다. **`status == APPROVED`일 때만 상품을 내준다.**

- 거절은 장애가 아니라 정상적인 업무 결과다. 결제 기록도 이미 남았다.
- 멱등 재현이 단순하다. 저장된 행을 읽어 같은 형태로 돌려주면 되고, HTTP 상태 코드를 따로 저장할 필요가 없다.
- 대안은 카드 거절을 4xx로 돌려주는 방식이다 (예: Stripe의 402). 가맹점이 상태 코드만 보고 분기할 수 있지만, 거절·망취소 완료·미확정을 각각 어느 코드에 둘지 또 정해야 한다.

**연결 실패는 망취소 없이 `DECLINED`로 끝낸다.** TCP 연결이 안 됐으면 전문이 한 바이트도 나가지 않았으므로 카드사 쪽 결과는 "없음"으로 확정된다. 연결된 뒤에 쓰기나 읽기가 실패하면 카드사가 받았을 수 있으므로 `UNKNOWN` → 망취소다. 기준은 **"보냈을 가능성이 있는가"**다.

## 2. 결과 코드

`result.code`는 카드사 응답코드(숫자 4자리)이거나, 카드사 응답이 없을 때 PG가 붙이는 내부 코드(`P` + 숫자 3자리)다. 승인과 취소에 같은 표를 쓴다.

| 코드 | 뜻 | 승인 결과 | 취소 결과 |
|---|---|---|---|
| `0000` | 정상 | `APPROVED` | `CANCELLED` |
| `1001`~`1003`, `9999` | 카드사 거절 ([02-message-spec.md](02-message-spec.md) 2장) | `DECLINED` | `FAILED` |
| `2001` | 원거래 없음 | — | `FAILED` |
| `2002` | 이미 취소됨 | — | `CANCELLED` (카드사 쪽 상태에 맞춘다) |
| `P001` | 카드사 연결 실패 (전송 안 됨) | `DECLINED` | `FAILED` |
| `P002` | 응답 확인 실패 (타임아웃, 전문 오류), 망취소 완료 | `NET_CANCELLED` | `NET_CANCELLED` |
| `P003` | 응답 확인 실패, 망취소도 실패 | `UNKNOWN` | `UNKNOWN` |

결과를 재현하려면 코드가 저장돼 있어야 하므로 `payment`와 `payment_cancel`에 `result_code`를 둔다 ([01-erd.md](01-erd.md)). 메시지는 코드 표에서 만든다.

## 3. 멱등성: `Idempotency-Key`

가맹점 → PG 구간에도 망취소와 똑같은 문제가 있다. 가맹점이 우리 응답을 못 받으면 결제가 됐는지 모른다. 그냥 다시 보내면 이중 결제가 된다. 그래서 가맹점은 요청마다 키를 만들고, 다시 보낼 때 같은 키를 쓴다. 같은 키는 한 번만 처리한다 (I2).

**INSERT를 먼저 하고, 중복 키 예외로 분기한다.**

```
INSERT payment (status = REQUESTED, merchant_id, idempotency_key, ...) → 커밋
  ├─ 성공 → 새 요청. 카드사로 전송
  └─ 중복 키 (ORA-00001 → Spring DuplicateKeyException) → 기존 행 조회
       ├─ 본문이 다름 → 422 IDEMPOTENCY_KEY_REUSED
       ├─ REQUESTED  → 409 PAYMENT_IN_PROGRESS (Retry-After: 5)
       └─ 그 외       → 저장된 결과로 201 재현 (Idempotent-Replayed: true)
```

- "조회해서 없으면 INSERT"로 하면 두 요청이 동시에 조회하고 둘 다 "없음"을 볼 수 있다. 결국 UNIQUE 제약이 두 번째를 막으므로 중복 키 처리는 어차피 필요하다. 그렇다면 조회를 먼저 할 이유가 없다.
- Oracle에서 첫 번째 세션이 커밋하기 전에 두 번째 세션이 같은 키를 INSERT하면, 두 번째 세션은 **기다린다.** 첫 번째가 커밋하면 ORA-00001, 롤백하면 INSERT가 성공한다. 첫 트랜잭션은 INSERT 하나라 금방 끝난다.
- **본문 비교용 컬럼을 따로 두지 않는다.** 저장된 `card_hash`(HMAC), `amount`, `installment_months`와 비교한다. 유효기간은 저장하지 않으므로 비교에서 빠진다.
- **거절된 결제를 같은 키로 다시 보내면 거절이 재현된다.** 다시 결제하려면 새 키를 써야 한다. 가맹점 연동 안내에 꼭 적어야 하는 규칙이다.
- 키는 v1에서 영구 보관한다 (UNIQUE). 보관 기간을 두고 지우는 건 완성선 이후.
- 400(키 없음), 409(처리 중), 422(본문이 다름) 구분은 IETF 초안 *The Idempotency-Key HTTP Header Field*의 오류 처리 규칙을 따랐다.

## 4. 동기 처리와 응답 시간 상한 27초

가맹점에 응답하기 전에 망취소까지 끝낸다. 그래서 가맹점은 항상 확정된 지시를 받는다. `UNKNOWN`도 "실패로 취급하라"는 지시다.

| 구간 | 최악 |
|---|---|
| 승인: 연결 1초 + 응답 대기 3초 | 4초 |
| 망취소 4회 × (연결 1초 + 응답 대기 3초) | 16초 |
| 재시도 사이 대기 1 + 2 + 4초 | 7초 |
| **합계** | **27초** |

가맹점 클라이언트의 읽기 타임아웃은 **30초 이상**으로 안내한다. 그래도 끊기면 같은 키로 재시도한다.

**카드사를 호출하는 동안 DB 트랜잭션을 잡지 않는다.** 트랜잭션을 둘로 나눈다.

1. `INSERT … REQUESTED` → 커밋
2. 카드사 호출 (트랜잭션 없음)
3. `UPDATE payment SET status = … WHERE payment_id = ? AND status = 'REQUESTED'` → 커밋 (I3)

하나로 묶으면 카드사가 느린 동안 DB 커넥션을 붙잡는다. 커넥션 풀이 10개이고 요청마다 27초를 잡으면 처리량은 10 ÷ 27초 ≈ **초당 0.37건**으로 떨어진다 (리틀의 법칙). 평소 피크 116 TPS를 감당할 수 없다. 나누면 커넥션은 INSERT와 UPDATE 순간에만 쓴다. 또 1번을 먼저 커밋하지 않으면, 전송 후 앱이 죽었을 때 "보냈을지도 모르는 거래"가 기록에 남지 않는다 ([00-domain.md](00-domain.md) 4장).

**HTTP 요청은 가상 스레드로 처리한다** ([ADR-0003](adr/0003-external-messaging.md), `spring.threads.virtual.enabled=true`). 카드사 장애로 모든 요청이 27초씩 걸리면, 동시에 붙잡힌 요청은 116 TPS × 27초 ≈ **3,100개**다. 플랫폼 스레드 풀(Tomcat 기본 200개)이면 바로 고갈된다. 가상 스레드는 블로킹되는 동안 OS 스레드를 놓아준다.

대안은 타임아웃 즉시 가맹점에 응답하고 망취소는 백그라운드로 돌리는 방식이다. 응답은 빠르지만, 백그라운드 작업이 앱 재시작에도 살아남게 하려면 작업 큐와 재시작 복구가 필요하다. v1 범위를 넘는다.

## 5. 취소

- **`Idempotency-Key`를 받지 않는다.** 취소는 결제 하나에 대한 동작이라 `txnId`가 그 역할을 한다. 이미 `CANCELLED`면 카드사에 보내지 않고 200으로 돌려준다.
- **실패한 취소는 다시 시도할 수 있어야 한다.** 취소가 `FAILED`나 `NET_CANCELLED`로 끝나면 결제는 여전히 `APPROVED`다. 그래서 `payment_cancel`의 UNIQUE(payment_id)를 함수 기반 유니크 인덱스로 바꿨다. 결과를 기다리거나 성공한 취소(`REQUESTED`, `UNKNOWN`, `CANCELLED`)만 결제당 하나로 제한한다 ([01-erd.md](01-erd.md)).
- **결과를 모르는 취소(`UNKNOWN`)가 있으면 새 취소를 막는다** (409 `CANCEL_PENDING`). 막지 않으면 이런 순서가 가능하다.
  1. 이전 취소가 실제로는 카드사에서 처리됐다.
  2. 새 취소는 `2002 이미 취소됨`을 받고, 우리는 `CANCELLED`로 기록한다.
  3. 그 뒤 이전 취소에 대한 망취소가 카드사에 닿아 이전 취소를 무효로 만든다. 카드사 쪽은 다시 승인 상태가 된다.

  두 전문의 처리 순서를 우리가 알 수 없으므로, 미확정 취소는 운영자가 카드사와 확인한다 (관리 화면은 완성선 이후).
- **취소 금액을 받는다.** v1은 전체 취소만이라 결제 금액과 같아야 한다 (다르면 422). 그래도 받는 이유는 두 가지다. 가맹점이 엉뚱한 결제를 취소하는 실수를 금액 대조로 잡을 수 있고, 부분 취소를 추가할 때 계약을 바꾸지 않아도 된다.
- 결제 상태는 `UPDATE payment SET status = 'CANCELLED' WHERE payment_id = ? AND status = 'APPROVED'`로 바꾼다 (I3).

## 6. 인증과 가맹점 격리

- `X-Api-Key`의 SHA-256으로 `merchant.api_key_hash`를 찾아 가맹점을 정한다. 가맹점번호를 본문으로 받지 않으므로 다른 가맹점 이름으로 결제하거나 취소할 수 없다.
- **다른 가맹점의 `txnId`는 404로 응답한다.** 403이면 "그 거래가 존재한다"는 정보를 주게 된다.
- **API 키는 HMAC 없이 SHA-256만으로 충분하다.** 카드번호는 모르는 자리가 6개라 후보가 10⁶개뿐이다 ([ADR-0005](adr/0005-card-data-protection.md)). API 키는 무작위 32바이트라 후보가 2²⁵⁶개여서 전수 대입이 불가능하다.
- `SUSPENDED` 가맹점은 승인·취소가 403이다. 조회는 허용한다. 정지 전 거래를 확인할 수 있어야 하기 때문이다.
- v1은 키 발급 API 없이 시드 데이터로 넣는다.

## 7. 카드번호가 새는 길 막기 (I10)

평문 카드번호는 요청 본문에만 있다. 받자마자 `card_enc`, `card_hash`, `card_masked`로 바꾸고, 평문은 0100 전문을 만들 때만 쓴다. 놓치기 쉬운 경로는 이렇다.

| 경로 | 대책 |
|---|---|
| 요청 record의 `toString()` | Java record는 모든 필드를 출력하는 `toString()`을 자동으로 만든다. `log.info("{}", request)` 한 줄로 카드번호가 샌다. `toString()`을 재정의해 마스킹한다. |
| 검증 실패 예외 | Spring의 검증 예외 메시지에는 거부된 값(rejected value)이 들어간다. 별도 처리기가 없으면 Spring MVC 기본 처리기가 이 메시지를 WARN 로그로 남긴다. 검증 예외를 직접 처리해 응답과 로그에 필드명과 이유만 남긴다. |
| 요청 본문 로깅 | 본문 전체를 남기는 로깅 필터를 쓰지 않는다. 꼭 필요하면 `cardNumber`, `cardExpiry`를 마스킹한 뒤 남긴다. |
| 전문 로그 | `message_log`는 마스킹 후 저장한다 ([ADR-0005](adr/0005-card-data-protection.md)). |

## 8. 입력 검증 범위

- 카드번호는 형식(숫자 16자리)만 본다. **Luhn 검증은 카드사(시뮬레이터)가 한다** (`1003`). 그래야 시뮬레이터의 Luhn 경로를 E2E 테스트로 확인할 수 있다. 실무 PG는 카드사 호출을 아끼려고 Luhn을 미리 검사하기도 한다.
- 유효기간도 형식만 본다. 만료 판단은 카드사 몫이다 (`1002`).
- 할부는 `0`(일시불) 또는 `2`~`36`개월이다. 국내 신용카드 할부는 보통 5만 원 이상 결제에만 허용되므로, 5만 원 미만 할부는 422 `INSTALLMENT_NOT_ALLOWED`다.
- 금액 상한은 전문 거래금액 필드(12자리)의 한도인 999,999,999,999원이다.
- 시각은 KST 오프셋(`+09:00`)을 붙여 내보낸다. DB는 KST `TIMESTAMP`로 저장한다 ([01-erd.md](01-erd.md)).

## 알려진 한계 (v1)

| 한계 | 결과 | 정리 방법 |
|---|---|---|
| `REQUESTED` 저장 후 서버가 멈춤 | 행이 `REQUESTED`로 남고, 같은 키로 재시도하면 계속 409 | 다음 날 대사에서 `UNKNOWN`과 같이 다룬다 ([04-batch.md](04-batch.md)). 미결 거래 정리 스케줄러는 완성선 이후 |
| 망취소 재시도 모두 실패 | `UNKNOWN`으로 남는다 | 다음 날 매입이 들어오면 대사에서 `STATUS_MISMATCH` |
| 멱등 키 영구 보관 | 인덱스가 계속 커진다 | 보관 기간 정책은 완성선 이후 |
