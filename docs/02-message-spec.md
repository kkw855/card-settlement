# 02. 전문·파일 명세

PG ↔ 가상 카드사의 TCP 전문, 카드사 → PG 매입 내역 파일, PG → 은행 지급 파일의 바이트 단위 명세.
**모든 길이와 오프셋은 바이트 기준**이다. 문자 수가 아니다.

## 1. 공통 규칙

### 인코딩
- **MS949** (EUC-KR의 확장, Java 이름 `MS949` 또는 `x-windows-949`).
- EUC-KR 완성형은 한글 2,350자만 표현한다. 현대 한글 11,172자를 모두 쓰려면 MS949가 필요하다 (예: "똠"은 EUC-KR에 없다).
- 한글 1자 = 2바이트, 영문·숫자 1자 = 1바이트. 같은 "홍길동"이 MS949로 6바이트, UTF-8로 9바이트다.

### 필드 타입

| 타입 | 정렬 | 채움 | 예 (길이 12) |
|---|---|---|---|
| `N` (숫자) | 오른쪽 | 왼쪽을 `0`으로 | `10000` → `000000010000` |
| `AN` (문자) | 왼쪽 | 오른쪽을 공백(0x20)으로 | `M001` → `M001␣␣␣␣␣␣␣␣` |

- `AN` 필드가 길이를 넘으면 자른다. **2바이트 문자를 반으로 자르지 않는다.** 자르는 위치가 문자 중간이면 그 문자를 빼고 공백 1바이트로 채운다.
  - 예: 길이 40에 `A` + 한글 20자(= 41바이트) → `A` + 한글 19자(39바이트) + 공백 1바이트
- `N` 필드에 숫자가 아닌 값이 오면 파싱 오류로 처리한다.

### TCP 프레이밍
```
[길이 4바이트, AN, 숫자 문자열][전문 N바이트]
```
- 길이 = 뒤따르는 전문의 바이트 수 (길이 필드 자신은 제외). 이 명세의 모든 전문은 150바이트이므로 `0150`.
- v1은 **거래마다 연결**한다 (연결 → 요청 → 응답 → 종료). 이유는 [ADR-0003](adr/0003-external-messaging.md).

### 타임아웃과 망취소
| 항목 | 값 |
|---|---|
| 연결 타임아웃 | 1초 |
| 응답 대기 (0100, 0400) | 3초 → 초과 시 거래는 `UNKNOWN`, 즉시 망취소 |
| 망취소 응답 대기 (0420) | 3초 |
| 망취소 재시도 | 최초 1회 + 재시도 3회, 재시도 전 대기 1초 → 2초 → 4초 |

최악의 경우 망취소 정리까지 4회 × (연결 1초 + 응답 대기 3초) + (1 + 2 + 4)초 = **23초**. 승인 요청 4초를 더하면 API 응답 상한은 **27초**다 ([03-api.md](03-api.md) 4장).

## 2. 전문 공통부 (모든 전문의 앞 50바이트)

| 오프셋 | 길이 | 타입 | 필드 | 설명 |
|---|---|---|---|---|
| 0 | 4 | N | 전문구분코드 | 아래 표 |
| 4 | 20 | AN | 거래고유번호 | PG가 생성. `P` + 날짜 8 + 일련번호 11 |
| 24 | 14 | N | 전송일시 | `yyyyMMddHHmmss` (KST) |
| 38 | 4 | AN | 응답코드 | 요청은 공백, 응답은 아래 표 |
| 42 | 8 | AN | 예비 | 공백 |

| 전문구분코드 | 뜻 |
|---|---|
| `0100` / `0110` | 승인 요청 / 응답 |
| `0400` / `0410` | 취소 요청 / 응답 |
| `0420` / `0430` | 망취소 요청 / 응답 |

(구분코드 체계는 국제 카드 전문 표준 ISO 8583의 메시지 유형 번호를 빌렸다.)

| 응답코드 | 뜻 |
|---|---|
| `0000` | 정상 |
| `1001` | 한도 초과 (거절) |
| `1002` | 유효기간 오류 |
| `1003` | 카드번호 오류 (Luhn 검증 실패 포함) |
| `2001` | 원거래 없음 |
| `2002` | 이미 취소됨 |
| `9999` | 시스템 오류 |

### 골든 샘플: 0100 승인 요청

코덱 테스트의 기준값. 양쪽(PG, 시뮬레이터)이 이 샘플로 각자 테스트한다.

|---|---|---|
| 길이 | `0150` | 4 |
| 전문구분코드 | `0100` | 4 |
| 거래고유번호 | `P2026100800000000001` | 20 |
| 전송일시 | `20261008103000` | 14 |
| 응답코드 | 공백 4 | 4 |
| 예비 | 공백 8 | 8 |
| 가맹점번호 | `M000000001` | 10 |
| 카드번호 | `4111111111111111` | 16 |
| 유효기간 | `2812` | 4 |
| 할부개월 | `00` | 2 |

## 4. 시뮬레이터 테스트 규칙

결과를 **거래금액의 끝 세 자리**로 조종한다 (결정적이라 테스트를 재현할 수 있다).

| 끝 세 자리 | 승인 단계 | 매입 파일 | 기대 대사 결과 |
|---|---|---|---|
| `001` | `1001` 거절 | — | — |
| `009` | 응답을 5초 지연 (카드사 쪽은 승인됨) → PG 타임아웃 → 망취소 | 망취소 처리되어 매입 없음 | 없음 (정상 정리) |
| `101` | 승인 | **매입 누락** | `UNCAPTURED` |
| `102` | 승인 | 매입 금액 **+10원** | `AMOUNT_MISMATCH` |
| `109` | 응답 5초 지연 → 망취소에 `0430 01`(취소함)로 응답하지만 **실제로는 취소하지 않음** | 매입됨 | `STATUS_MISMATCH` (우리는 `NET_CANCELLED`) |
| `119` | 응답 5초 지연 + **망취소에 응답하지 않음** → 재시도 모두 실패 | 매입됨 | `STATUS_MISMATCH` (우리는 `UNKNOWN`) |
| 그 외 | 승인 | 정상 매입 | `MATCHED` |

- 카드번호가 Luhn 검증에 실패하면 `1003`.
- 매입 파일 생성 시 옵션 `--inject-foreign=N`이면 우리에게 없는 거래 N건을 추가한다 → `CAPTURE_ONLY`.
- `119`는 망취소 재시도를 끝까지 도는 경로라 테스트가 27초 걸린다. 테스트에서는 타임아웃과 대기 시간을 설정으로 줄인다.

**카드사 처리 규칙 (취소·망취소)**

| 요청 | 조건 | 응답 |
|---|---|---|
| 0400 취소 | 원거래고유번호로 찾고, 원승인번호·원승인일자·가맹점번호가 모두 맞아야 같은 거래로 본다. 하나라도 다르거나 망취소된 거래면 | `2001` 원거래 없음 |
| | 이미 취소된 거래 | `2002` 이미 취소됨 |
| | 취소금액 ≠ 원거래 금액 (v1은 전체 취소만) | `9999` |
| | 그 외 | `0000`, 취소 승인번호를 새로 발급 |
| 0420 망취소 (원전문 `0100`) | 원거래가 있으면 무효로 만든다 (`109`, `119`는 위 표대로) | `01` 원거래를 취소함 |
| | 원거래가 없으면 (0100이 카드사에 닿지 않음) | `02` 원거래가 없었음 |
| 0420 망취소 (원전문 `0400`) | 그 취소가 있으면 무효로 만들고 승인 상태로 되돌린다. 다시 취소할 수 있다 | `01` |
| | 그 취소가 없으면 | `02` |

- 망취소 응답의 응답코드는 `01`, `02` 모두 `0000`이다. PG 입장에서는 둘 다 "원거래가 무효다"라는 같은 결과다.
- **같은 망취소를 다시 보내도 결과가 같다.** PG가 0430을 못 받아 재시도해도 안전하다.

**매입 기준** — 시뮬레이터는 매입일 B의 파일을 만들 때 아래 규칙을 따른다. 대사 SQL([04-batch.md](04-batch.md))이 같은 규칙을 기대한다.

| 거래 | B 파일에 들어가는 레코드 |
|---|---|
| B−1일 승인, B−1일 24:00까지 취소되지 않음 | `01` 매입 |
| B−1일 승인, B−1일 안에 취소됨 | 없음 (매입 전 취소) |
| B−1일 이전 승인, B−1일에 취소됨 | `02` 매입취소 |
| 망취소된 거래 | 없음 (`109`, `119` 제외) |

## 5. 파일 공통 규칙

- 레코드 길이 150바이트 고정, 레코드 사이에 CRLF(2바이트, 레코드 길이에 포함하지 않음).
- 구조: 헤더(H) 1개 → 데이터(D) 0개 이상 → 트레일러(T) 1개.
- **트레일러의 건수와 합계가 데이터 레코드와 다르면 파일 전체를 거부한다** (I4).
